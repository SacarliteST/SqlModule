# SQLModule — Цели дальнейшей разработки (ROADMAP)

Документ фиксирует scope и решения по развитию модуля после готового CRUD.
Дополняет `CONCEPT.md`. Принцип: сначала рабочая демка проверки `SELECT`-запросов,
затем — нечёткое сравнение, пул контейнеров и цифровой след.

---

## 1. Цель демки (Фаза 1)

Рабочий цикл «песочницы» end-to-end:

1. Преподаватель **конструирует схему БД** (таблицы/колонки/типы) в UI.
2. Система **генерирует DDL** из мета-модели и **валидирует** его прогоном в одноразовом
   контейнере (СУБД из `DbmsDictionary`). Ошибок нет → схема **сохраняется как мета-сущности**
   (`MetaTable`/`MetaAttribute`/`MetaRelationship`). Есть ошибка → понятный ответ, ничего не сохраняем.
3. Преподаватель **наполняет схему данными** в UI → `DataRecord` (строка) + `CellValue` (значение ячейки), EAV.
4. После финализации **схема и данные становятся неизменными**.
5. Преподаватель создаёт задание `SqlTask` (тема, целевая схема, текст, эталонный `SqlQuery`).
   При создании эталона его результат **вычисляется один раз** в материализованной песочнице и
   сохраняется как «золотой» результат.
6. Студент отправляет **`SELECT`-решение** → оно выполняется в песочнице (read-only) → результат
   **сравнивается с золотым** → создаётся `Attempt` (решение + результат + вердикт).

---

## 2. Область Фазы 1

Делаем:
- Только запросы **выборки данных (`SELECT`)** от студента; исполнение read-only.
- **Две СУБД (хардкод): PostgreSQL и MySQL/MariaDB** — абстракция диалектов с двумя реализациями.
- Конструктор схемы → генерация DDL → валидация в контейнере → сохранение как меты.
- Наполнение данными через `DataRecord`/`CellValue`.
- Эталонный результат фиксируется один раз при создании `SqlQuery`.
- Проверка решения: **точное сравнение — одинаковый набор строк в одинаковом порядке**.
- Одна сущность `Attempt` (решение + результат + вердикт).
- Контейнер поднимается **на каждую проверку** (пул — позже).

НЕ делаем на Фазе 1:
- Проверку эффективности (индексы, планы выполнения) — только корректность выборки.
- DML/DDL от студента (только `SELECT`).
- Нечёткое сравнение и проверку по ключевым словам (Фаза 2).
- Редактирование схемы после финализации.
- Цифровой след, события, SignalR (Фаза 2).
- Пул контейнеров (Фаза 2).

## 4. Цели по областям

### A. Жизненный цикл схемы (конструктор → валидация → меты → данные)
- Генератор DDL из мета-модели; **абстракция диалектов** с реализациями Postgres и MySQL.
- Валидация схемы прогоном DDL в одноразовом контейнере **до** сохранения (атомарно: либо всё, либо ничего).
- Сохранение валидной схемы как мета-сущностей.
- Наполнение данными из EAV (`DataRecord`/`CellValue`) и их материализация в `INSERT` при прогоне.
- Финализация схемы → неизменяемость.

### B. Движок песочницы `ISandboxExecutor` (обобщение `IDbmsProbe`)
- Поднять контейнер из `DbmsDictionary` → применить DDL + данные → выполнить запрос → вернуть строки/ошибку.
- Один движок на три задачи: валидация схемы, вычисление эталонного результата, прогон решения студента.
- Read-only исполнение решения студента: read-only роль/транзакция, **таймаут запроса**, **лимит строк**.
- Фейк-реализация для тестов (как `AlwaysOkProbe`); реальный Docker — отдельной категорией тестов.
- Диалекты: Postgres и MySQL/MariaDB.

### C. Модель попытки (одна сущность `Attempt`)
Хранит: `SubmittedSql`, `Status` (Running/Succeeded/Failed/Error/TimedOut), `IsCorrect`,
`RowCount`, `DurationMs`, `ErrorMessage`, причину несоответствия, `TaskId`, `UserId`, тайминги.
Без разнесения на отдельные Submission/Result.

### D. Слайс `SubmitAttempt`
Центральный сценарий: выполнить решение в песочнице → сравнить с золотым результатом →
сохранить `Attempt`. Приоритетнее оставшегося CRUD.

### E. Эталон и «золотой» результат
- При создании `SqlQuery` прогнать его в материализованной песочнице, сохранить набор колонок +
  упорядоченные строки как эталонный результат задачи.
- Хранить в **JSON/JSONB поле сущности `SqlQuery`** (колонки + упорядоченные строки).

### F. Безопасность и устойчивость исполнения
- Read-only, таймаут, лимит строк, изоляция и гарантированная очистка контейнера.
- Безопасные сообщения об ошибках наружу (не раскрывать внутренности).

---

## 5. Алгоритм проверки (Фаза 1)

```
SubmitAttempt(taskId, submittedSql)
│
├── Запрет не-SELECT (read-only)
├── Материализовать песочницу задачи: контейнер из DbmsDictionary → DDL схемы → INSERT данных
├── Выполнить submittedSql (read-only, timeout, row-limit) → actualRows | error
├── Сравнить actualRows с «золотым» результатом задачи:
│       строки и порядок совпадают? значения по позиции колонок совпадают?
├── Сформировать Attempt: SubmittedSql, Status, IsCorrect, RowCount, DurationMs, ErrorMessage, Reason
└── Сохранить Attempt
```

Причины вердикта: `Ok`, `RowCountMismatch`, `ValueMismatch`, `OrderMismatch`, `SqlError`, `Timeout`.

---

## 6. Фаза 2 (после демки)

- **Нечёткое сравнение**: студент может писать запрос иначе, но корректно; маски на имена колонок.
- **Проверка по ключевым словам**: контроль того, *как* решено (наличие требуемых конструкций),
  и/или гибкое сопоставление колонок.
- **Пул контейнеров** вместо поднятия на каждую проверку.
- **Цифровой след**: события (ввод, запуски, ошибки, тайминги) в JSONB + SignalR, интеграция в ядро Scoodle.
- Возможное расширение набора СУБД и проверка эффективности (планы/индексы).
