# Техническое задание: Фаза 2a — тёплый пул sandbox-контейнеров

## 1. Назначение

Фаза 2a должна уменьшить задержку выполнения SQL за счёт повторного использования заранее
запущенных контейнеров PostgreSQL и MySQL/MariaDB. Сейчас
`TestcontainersSandboxExecutor` создаёт контейнер для каждого вызова `RunAsync`,
`ValidateSetupAsync` и `InspectDdlAsync`, а затем уничтожает его. Запуск СУБД составляет
значительную и нестабильную часть времени ответа.

Пул является внутренней оптимизацией модуля. Публичный HTTP API, Swagger, Orval-клиент,
сущности `Attempt` и `ModuleSession`, правила проверки решения и интеграционные события в этой
фазе не изменяются.

## 2. Границы фазы

В рамках Фазы 2a требуется:

- ввести абстракцию аренды sandbox-воркера;
- реализовать локальный ограниченный пул на одном Docker-host;
- заранее запускать минимальное число контейнеров для разрешённых профилей СУБД;
- изолировать каждый прогон в отдельной временной БД внутри арендованного контейнера;
- разделить control-admin, ограниченного setup-owner и read-only пользователя выполнения;
- гарантированно очищать окружение перед возвратом контейнера в пул;
- восстанавливать размер пула после сбоя контейнера;
- добавить наблюдаемость, feature flag, безопасное выключение и возможность отката;
- провести Docker-интеграционные, нагрузочные и soak-проверки.

Не входят в Фазу 2a:

- составной скоринг, веса критериев и AST-анализ;
- новые поля заданий и попыток;
- изменение лимитов попыток и финализации сессии;
- скрытые наборы данных и вторая учебная БД;
- распределённый lease и таблица аренд в PostgreSQL;
- поддержка нескольких Docker-host;
- Kafka-событие на каждую попытку и журнал преподавателя;
- изменение `IDbmsProbe`: его короткоживущие проверочные контейнеры остаются отдельным
  механизмом.

## 3. Совместимость

Сохраняются без изменения:

- интерфейс `ISandboxExecutor` и семантика его трёх методов;
- различие между инфраструктурной ошибкой (`Result.Fail`) и SQL-ошибкой пользовательского
  запроса (`QueryResultSet.Succeeded = false`);
- таймаут SQL-команды, лимиты строк и длины SQL;
- read-only выполнение решения и обязательный `ROLLBACK`;
- коды ошибок, HTTP-статусы и формат ответов существующих endpoints;
- fake sandbox в профиле `Isolated` и в быстрых интеграционных тестах.

Если для внутренней диагностики понадобятся новые коды ошибок, наружу они должны отображаться
на уже существующую категорию инфраструктурного сбоя sandbox. Расширение публичного ProblemDetails
в эту фазу не входит.

## 4. Целевая архитектура

### 4.1. Компоненты

В проекте `Sandbox` необходимо выделить:

1. `ISandboxLeaseManager` — выдаёт эксклюзивную аренду воркера для нормализованного профиля СУБД.
2. `LocalSandboxLeaseManager` — локальная реализация с ограниченной очередью ожидания на базе
   `Channel<T>` либо `SemaphoreSlim`. Персистентное хранилище аренд не используется.
3. `SandboxWorker` — внутреннее описание контейнера, административного подключения, профиля,
   поколения и текущего состояния.
4. `SandboxLease` — одноразовый `IAsyncDisposable`-объект. Только его владелец может работать с
   воркером; повторное освобождение не должно менять состояние пула.
5. `SandboxPoolHostedService` — прогрев, периодическая проверка здоровья, восполнение пула и
   корректное завершение.
6. `PooledSandboxExecutor` — сохраняет контракт `ISandboxExecutor`, но выполняет операцию через
   lease и временную БД.
7. Текущий одноразовый исполнитель — сохраняется как fallback-реализация и должен быть
   переименован так, чтобы назначение было однозначным, например `OneShotSandboxExecutor`.

### 4.2. Ключ профиля

Пул ведётся отдельно для каждой допустимой конфигурации:

`SystemName + DockerImage + DefaultPort + environment fingerprint`.

Пароли не входят в логи и метрики; fingerprint вычисляется как стабильный хеш нормализованных
параметров. Нельзя отдать Postgres-воркер запросу MySQL либо контейнер другого образа.

Профиль должен поступать только из уже валидированного `DbmsDictionary`. Фаза 2a не расширяет
возможность пользователя передавать произвольный Docker image.

### 4.3. Состояния воркера

Допустимые переходы:

```text
Starting -> Ready -> Leased -> Recycling -> Ready
    |         |        |           |
    +---------+--------+-----------+-> Unhealthy -> Disposed -> replacement
```

- `Ready`-воркер находится ровно в одной очереди соответствующего профиля.
- `Leased`-воркер принадлежит ровно одному lease.
- Воркеры `Starting`, `Recycling`, `Unhealthy` не выдаются потребителям.
- Поколение lease проверяется при возврате, чтобы устаревший dispose не вернул уже заменённый
  воркер.
- Общее число живых и запускаемых воркеров профиля не превышает `MaxSize`.

## 5. Жизненный цикл аренды

Для каждого `RunAsync`, `ValidateSetupAsync` или `InspectDdlAsync` исполнитель обязан:

1. Нормализовать профиль СУБД и запросить lease с ограниченным временем ожидания.
2. Через control-admin подключение создать уникальную временную БД. Имя генерируется
   сервером из случайного идентификатора и не содержит пользовательский ввод.
3. Создать временных setup-owner и runner с доступом только к этой БД.
4. Подключиться к временной БД и применить setup-операторы от setup-owner без серверных и
   межбазовых привилегий.
5. Для `RunAsync` выполнить пользовательский SQL через runner-подключение в read-only
   транзакции. Для `ValidateSetupAsync` и `InspectDdlAsync` сохранить текущую семантику.
6. Закрыть все подключения к временной БД.
7. Администратором принудительно завершить оставшиеся сессии этой БД, удалить временную БД и
   проверить результат очистки.
8. Вернуть воркер в `Ready` только после успешной очистки. При любой неопределённости пометить
   контейнер `Unhealthy`, удалить его и запустить замену.

Для PostgreSQL единицей изоляции является отдельная database. Для MySQL/MariaDB — отдельная
database/schema. Переиспользование одного и того же namespace между арендами запрещено.

## 6. Разделение привилегий

Контейнер запускается с техническими учётными данными control-admin, известными только модулю.
Он используется исключительно для создания/удаления временной БД, пользователей и принудительного
завершения соединений. Пользовательский DDL и seed выполняются временным setup-owner, который
может управлять объектами только внутри своей БД, но не имеет superuser, файловых, системных или
межбазовых привилегий. Пользовательский запрос выполняется отдельным runner-пользователем.

Runner должен:

- иметь право подключения и чтения данных только текущей временной БД;
- не иметь прав на создание/изменение/удаление объектов и данных;
- не иметь административных, файловых и межбазовых привилегий;
- не иметь доступа к временным БД других lease;
- сохранять защиту read-only транзакцией и `ROLLBACK` как второй уровень ограничения.

Пароли генерируются приложением, не возвращаются клиенту, не пишутся в логи и не используются
как label контейнера.

## 7. Конкурентность и ограничение ресурсов

- Размер пула задаётся отдельно для каждого профиля через `MinSize` и `MaxSize`.
- `MinSize >= 0`, `MaxSize >= 1`, `MinSize <= MaxSize`; ошибочная конфигурация останавливает
  запуск приложения через `ValidateOnStart`.
- Ожидание lease ограничено `AcquireTimeoutSeconds` и поддерживает cancellation вызывающего
  запроса.
- Отмена HTTP-запроса не отменяет обязательную очистку: она выполняется с отдельным внутренним
  cleanup-timeout.
- Истечение acquire-timeout не должно порождать контейнер сверх `MaxSize`.
- Параллельные запросы одного профиля не должны блокировать выдачу воркеров другого профиля.
- Контейнеры запускаются с заданными лимитами CPU, памяти и процессов, без privileged mode,
  host-network и пользовательских bind mounts.

## 8. Отказы и восстановление

| Ситуация | Требуемое поведение |
|---|---|
| Нет свободного воркера до таймаута | Завершить операцию существующей инфраструктурной ошибкой; не обходить лимит новым one-shot контейнером |
| Ошибка старта/health check | Удалить воркер, применить ограниченный exponential backoff и попытаться восполнить `MinSize` |
| Ошибка создания временной БД или setup | Вернуть текущую ошибку setup, очистить namespace; при сомнительной очистке заменить контейнер |
| SQL-ошибка студента | Вернуть `Succeeded=false`, затем штатно очистить и переиспользовать воркер |
| Таймаут или отмена SQL | Прервать запрос/соединение, очистить; грязный воркер заменить |
| Ошибка cleanup | Никогда не возвращать воркер в `Ready`; удалить и заменить |
| Неожиданная остановка контейнера | Завершить текущую аренду инфраструктурной ошибкой, удалить дескриптор, восполнить пул |
| Остановка приложения | Прекратить новые аренды, дождаться активных до shutdown-timeout, затем удалить все контейнеры пула |

Цикл восстановления обязан иметь backoff и jitter, чтобы недоступный Docker daemon не создавал
бесконечный плотный цикл запуска.

## 9. Feature flag и откат

Режим выбирается при старте приложения:

- `Sandbox:Pool:Enabled=false` — используется существующий one-shot executor;
- `Sandbox:Pool:Enabled=true` — используется pooled executor.

Автоматический переход на one-shot при исчерпании пула запрещён: он обходит заданный предел
конкурентности. Допускается только явное переключение конфигурации с перезапуском приложения.
Это даёт предсказуемый rollback без изменения API и данных.

## 10. Конфигурация

Предлагаемая секция (точные имена становятся контрактом конфигурации после реализации):

```json
{
  "Sandbox": {
    "ContainerStartupTimeoutSeconds": 120,
    "DefaultQueryTimeoutSeconds": 15,
    "Pool": {
      "Enabled": false,
      "AcquireTimeoutSeconds": 15,
      "PreparationTimeoutSeconds": 30,
      "CleanupTimeoutSeconds": 15,
      "ShutdownTimeoutSeconds": 30,
      "HealthCheckIntervalSeconds": 15,
      "RestartBackoffMaxSeconds": 60,
      "Profiles": {
        "postgres": { "MinSize": 1, "MaxSize": 2 },
        "mysql": { "MinSize": 0, "MaxSize": 1 }
      }
    }
  }
}
```

Дефолт `Enabled=false` обязателен для первого релиза. Настройки профиля сопоставляются с
`SystemName` без учёта регистра; неизвестный профиль не должен молча получать неограниченный пул.

## 11. Наблюдаемость

Нужны структурированные логи с `profile`, внутренними `workerId`, `leaseId`, стадией и длительностью.
В логах запрещены SQL, значения учебных данных, пароли и полные connection strings.

Минимальные метрики:

- gauge: ready, leased, starting/recycling и unhealthy workers по профилю;
- counter: созданные/удалённые контейнеры, acquire timeout, cleanup failure, replacement;
- histogram: ожидание lease, подготовка временной БД, выполнение, очистка, полный цикл;
- counter: активные запросы и принудительные завершения при shutdown.

Существующий health endpoint должен отражать недоступность пула, если `Enabled=true` и ни один
настроенный обязательный профиль с `MinSize > 0` не способен достичь готового состояния после
startup grace period. Кратковременная замена одного воркера не должна немедленно переводить весь
сервис в unhealthy.

## 12. Безопасность

- Docker image берётся только из проверенного справочника и в эксплуатации фиксируется digest
  либо точным version-tag, не `latest`.
- Контейнеры пула имеют labels владельца, профиля и instance-id для диагностики и очистки сирот.
- Контейнеру не передаются Docker socket, секреты основного приложения и каталоги хоста.
- Временный namespace, setup-owner и runner credentials уникальны для каждой аренды.
- Данные одного lease не должны быть доступны следующему lease или параллельному воркеру.
- Приложение удаляет только контейнеры со своим instance-id; широкая очистка по image запрещена.
- Удаление контейнеров и временных БД должно быть идемпотентным.

## 13. Тестирование

### 13.1. Unit

Покрыть машину состояний, максимальный размер, FIFO/справедливую выдачу, cancellation,
acquire-timeout, повторный dispose, поколение lease, замену unhealthy-воркера, backoff и graceful
shutdown. Docker в этих тестах заменяется управляемым fake worker factory.

### 13.2. Docker integration

Для PostgreSQL и MySQL/MariaDB проверить:

- контейнер действительно повторно используется несколькими последовательными операциями;
- таблицы и данные первого lease отсутствуют во втором;
- два параллельных lease не видят данные друг друга;
- runner не может выполнить DDL/DML и обратиться к чужой БД;
- плохой setup, SQL-ошибка, timeout и cancellation не оставляют грязный воркер;
- ошибка cleanup приводит к замене контейнера;
- число контейнеров никогда не превышает `MaxSize`;
- после остановки test host не остаются контейнеры его instance-id;
- one-shot режим проходит прежние тесты без изменения поведения.

### 13.3. Нагрузочная проверка

Сравнить one-shot и pool на одном стенде, одном наборе схем и одинаковой конкуренции. Фиксировать
p50/p95/p99 полного запроса, ожидание lease, throughput, CPU/RAM Docker-host, число стартов и
ошибок. Минимальный прогон: 100 последовательных операций, burst `2 * MaxSize` и soak не менее
30 минут.

## 14. Приёмочные критерии

Фаза 2a считается готовой, когда одновременно выполнено следующее:

1. Публичные контракты и результаты функциональных сценариев не изменились.
2. Нет утечки таблиц, строк, пользователей или прав между lease в Docker-тестах.
3. Ни один воркер не выдаётся двум потребителям и ни один грязный воркер не возвращается в пул.
4. Лимит `MaxSize` соблюдается при burst, timeout и сбоях старта.
5. После graceful shutdown нет контейнеров с instance-id завершённого процесса.
6. Включение/выключение пула выполняется конфигурацией и проверено после перезапуска.
7. На контролируемом benchmark p95 полного sandbox-вызова после прогрева не хуже one-shot и
   показывает целевое улучшение не менее 30%; если порог не достигнут, результаты и bottleneck
   документируются до решения о rollout.
8. 30-минутный soak не показывает роста числа контейнеров, временных БД, подключений и памяти от
   итерации к итерации.
9. Unit, обычные integration и Docker integration тесты проходят.
10. Обновлены конфигурация, эксплуатационный runbook и инструкции rollback.

## 15. Порядок внедрения

1. Зафиксировать baseline one-shot режима.
2. Реализовать интерфейсы, конфигурацию и локальный координатор без подключения к production path.
3. Реализовать контейнерный worker и безопасную изоляцию аренды.
4. Подключить pooled executor за выключенным feature flag.
5. Добавить наблюдаемость и полный набор тестов.
6. На тестовом стенде включить малый пул: PostgreSQL `1..2`, MySQL `0..1`.
7. Выполнить smoke, burst и soak, сравнить с baseline.
8. После стабильности 2a отдельно принять решение о старте Фазы 2b.

Развёртывание на VPS выполняется только отдельной явной командой владельца проекта.
